# ADR 0008: Best-effort Web Push reminders

- **Status:** Accepted
- **Date:** 2026-11-26

## Context

US-11 requires reminders 10 minutes and 1 minute before an event, including delivery while the app is closed. The product must not claim reliability or platform coverage it cannot evidence. Browser automation is not installed, and push delivery depends on browser/platform support. The user delegated remaining decisions with the recommendation as the chosen option.

## Decision

- Delivery uses the Web Push standard with VAPID keys generated by the project itself; no external push provider is introduced. VAPID keys come from environment variables documented in `apps/api/.env.example` and are never committed.
- Permission is requested only from an explicit "Ativar lembretes" action. Denied, unavailable, or revoked permission produces a clear non-blocking message and leaves the rest of the calendar usable; the app never prompts again automatically.
- Subscriptions are stored per signed-in user and device. Sign-out unsubscribes only the current device. Push endpoints answering `404`/`410` are removed automatically.
- Creating or editing an event schedules the 10-minute and 1-minute instants from the saved instant. Offsets already in the past are skipped. Editing replaces only pending reminders, preserving already sent ones. Deleting cancels pending reminders and cascades the rest.
- A backend scheduler checks due reminders every 15 seconds and attempts one delivery per subscription. Failures are logged and recorded; there is no retry queue in the MVP.
- Supported platforms are browser-dependent. Chromium and Firefox desktop/Android can deliver to an installed or open-capable PWA; iOS support is limited to supported installed-PWA versions. The UI states that delivery is best-effort and may be unavailable.

## Consequences

- The core reminder behavior is implemented without adding a hosted provider or collecting extra personal data beyond the push subscription.
- The product does not guarantee delivery: permission, browser support, service-worker registration, and push endpoint availability are all visible limits.
- QA can verify scheduling, validation, public-key configuration, permission-state messaging in code, and payload handling in the service worker, but cannot execute real closed-app delivery without browser automation and a real push endpoint.
- Later work may add retries, delivery receipts, or a hosted provider without changing the event-scheduling contract.
