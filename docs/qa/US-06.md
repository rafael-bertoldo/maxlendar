## Riscos/defeitos

- **Baixo — Data inválida também marca o horário como inválido.** `apps/web/src/features/events/EventForm.tsx:64-70`. O helper retorna `null` tanto para data impossível quanto para hora impossível; o código responde com erro em `date` **e** em `time`. Exemplo executado: `2026-02-30 10:30` → `null`, mas a UI estática mostraria as duas mensagens. O campo correto aparece, porém um campo válido é acusado.
- **Baixo — Erro `field=timeZone` da API não é associado a um campo visível.** `apps/web/src/features/events/EventForm.tsx:90-98`. A API devolveu `400 field=timeZone`; o formulário só mapeia `title` e `startsAt`, mostrando o texto como erro geral. Como o fuso vem de `Intl` e não é digitável, o impacto é limitado, mas um valor inesperado do dispositivo não gere indicação por campo.
- **Baixo — `401` durante a criação não encerra a sessão na UI.** `apps/web/src/features/events/EventForm.tsx:90-101` versus `apps/web/src/features/calendar/CalendarPage.tsx:51-53`. O `POST` sem cookie retornou `401 UNAUTHENTICATED`; na criação, esse erro vira apenas `formError`, sem `onSessionExpired`, podendo manter a interface aparentemente autenticada até o próximo `GET`.
- **Baixo — Proteção contra duplo clique depende apenas do estado visual do botão.** `apps/web/src/features/events/EventForm.tsx:53,81,171-173`. `isSubmitting` é ativado antes do `await`, mas não há verificação imperativa no início de `handleSubmit`; a inexistência de duplicação não foi comprovada em navegador.
- **Baixo — Fechar o diálogo durante o envio não cancela a requisição.** `apps/web/src/features/events/EventForm.tsx:35-41,83-89` e `apps/web/src/shared/api/events.ts:40-53`. Não há `AbortSignal` em `createEvent`; se o usuário pressionar Escape enquanto salva, o sucesso ainda chama `onCreated` e altera a navegação.

**Defeito bloqueante: nenhum identificado.** Com base nas evidências executadas e na revisão estática, os critérios centrais de US-06 foram atendidos; os itens acima são de baixo impacto e não impedem a criação manual de um evento único.

## Limitações

- Sem Playwright/Puppeteer/Chrome: todos os itens de UI são **revisão estática**, não testes executados. Não houve verificação de clique, Escape real, foco, responsividade ou renderização em navegador.
- Datas e fusos foram simulados por `TZ` no Node e por `Intl` no ambiente de teste, não por dispositivos/browsers reais. O ajuste DST foi observado em `America/New_York`; em UTC não existe transição para essa data.
- Horários ambíguos de outono (por exemplo, `2026-11-01 01:30` em `America/New_York`) não foram executados; a decisão delega a resolução ao `Date` do navegador, conforme ADR 0004.
- A API foi executada na porta 3125 com o `dev.db` gitignored existente, sem reset ou exclusão. A conta descartável `qa_us06_bfedb1c_1795689000` e seu evento permanecem no banco.
- O projeto não possui script de testes automatizados; as evidências são comandos manuais, build, execução direta do helper e requisições `curl`.
- A confirmação de "exatamente um evento por criação bem-sucedida" usa uma criação bem-sucedida; não foi executado um cenário com duas criações válidas consecutivas.

## Recomendações

1. Ajustar `EventForm.tsx:64-70` para atribuir erro de data somente quando a data for inválida e erro de horário somente quando o horário for inválido, preservando a mensagem combinada apenas quando ambos falharem.
2. Mapear `field=timeZone` para um aviso explícito e tratar `ApiError.status === 401` com `onSessionExpired()`, alinhando `POST` ao caminho de `GET`.
3. Adicionar guarda `if (isSubmitting) return` no início de `handleSubmit` e/ou um `AbortSignal` em `createEvent` para cobrir duplo clique e fechamento durante o envio com evidência executável.
4. Instalar automação de navegador e registrar testes para: happy path, erros por campo, Escape, duplo clique, DST e sucesso com atualização de dia/âncora/refetch; isso transformaria a revisão estática em evidência executada.
5. Incluir a renderização do fuso do espectador e, quando útil, da proveniência no cartão do evento, fechando completamente a consequência do ADR 0004 em US-07.
6. Adicionar testes automatizados de API para contagem pós-`POST`, campos do DTO e validações, mantendo a execução manual atual como evidência suplementar.
